A complete walkthrough of the storefront, admin console, and B2B wholesale portal — every login, route, and feature, as currently implemented.

1. Architecture Overview

The platform is a two-app monorepo: a React single-page app (frontend/) talking to a REST API (backend/) mounted under /api/v1. There are three independent authentication systems — Customer, Admin, and B2B — each with its own JWT stored in an httpOnly cookie, so a login in one role never grants access to another.

Frontend stack

  • React 19, React Router 7
  • Redux Toolkit (cart, auth, wishlist, B2B draft-quote state)
  • Tailwind CSS 4
  • Axios (shared instance, cookie credentials on)
  • Google Maps JS API (Places + Geocoding)
  • Razorpay Checkout.js

Backend stack

  • Express 5, MongoDB via Mongoose
  • JWT + httpOnly cookies per role
  • Cloudflare R2 for product images
  • Razorpay Node SDK
  • Resend for transactional email (OTPs / password reset)
  • Helmet, rate limiting, custom sanitize middleware

2. Logins

Customerchanged

Email + OTP, no password — switched this round from mobile-number OTP (which had no real SMS provider behind it; it only ever simulated delivery) to real email delivery via Resend. A single flow handles both signup and login: if the email isn't recognized, the customer is asked for a name and an account is created on OTP verification. New signups — and any existing account that doesn't have a mobile number on file yet — are then required to enter and verify an Indian mobile number before a full login session is issued; the account row exists in the database at that point, but no session cookie is granted until this step completes.

5. Product Ratingsnew

Every product now has a display rating — an average (0–5 stars) and a count of "people rated" — shown on product cards and the product detail page, and usable for "Sort by Rating" on the catalog.

Admin-entered, not yet computed from real reviews. Since the storefront is only just launching, these numbers are set directly by the admin on the product form (/admin/products) rather than calculated from the Review collection. A product with no rating set shows a "New" badge instead of stars/zero. Genuine customers can still rate & review products (prompted after delivery, moderated by admin at /admin/reviews) — that data is collected in parallel and is intended to eventually replace the admin-set number once there's enough real review volume, but that switch-over has not been built yet.

Two related bugs were fixed as part of this: the product detail page's star rating used to be hardcoded to 5 stars for every product regardless of its actual rating, and the catalog's "Sort by Rating" was a silent no-op because the backend had neither a rating field to sort by nor a query-param-aware sort at all.

6. Payments

Cash on Delivery is the default and always available. Razorpay is fully live and has been verified with a real completed test transaction — order creation, the checkout modal, signature verification, and order confirmation all work end to end. If RAZORPAY_KEY_ID/RAZORPAY_KEY_SECRET in backend/.env are ever blanked out, attempting to pay online returns a clear "not configured yet" error rather than failing silently — it never crashes the server either way.

How it works: the backend computes the charge amount itself — from the customer's live server-side cart for a normal checkout, or from the specific item(s) requested for a Buy Now purchase — it never trusts a client-supplied amount, which is the standard payment-security practice (a client could otherwise tamper with what it pays). POST /customer/payments/razorpay-order creates the Razorpay order sized to that amount; the frontend opens Razorpay's Standard Checkout modal with it; on success, POST /customer/payments/razorpay-verify checks the HMAC-SHA256 signature Razorpay returns before creating the real order, decrementing stock, and (for a cart checkout) clearing the cart.

9. Known Limitations

  • Admin Quotes tab date-range filtering isn't exposed in the UI — GET /api/v1/admin/quotes accepts dateFrom/dateTo alongside status, but the B2B Team page's Quotes tab UI only exposes a status dropdown (search now works correctly as of this round — that part of the earlier limitation is resolved).
  • Mobile number is validated, not OTP-verified — the Indian mobile number collected right after email verification is format- and uniqueness-checked, but (unlike email) no confirmation code is sent to it. This is a deliberate scope choice for this round, not an oversight; adding a second, mobile-based OTP step is a possible future enhancement if it's ever needed.
  • The home page's decorative "Shop by category" tiles are static content (curated imagery in a fixed 3-tile layout), separate from the real, admin-managed Category system used everywhere else (product forms, filters, B2B catalog).
  • No order/quote-status confirmation emails — order placement, quote approval/rejection, etc. remain visible in-app only; Resend is currently used only for OTP flows and the optional contact-form admin notification.
  • Product ratings are admin-entered, not computed from real reviews — a deliberate interim state for launch (see Section 5), not a bug; genuine review collection is running in parallel for a future switch-over.
  • Newsletter subscription is capture-only — no admin page to view/export subscribers (the data and a listing endpoint exist, just no screen for it yet), no unsubscribe flow, no campaign sending.
  • B2B member deletion has no admin UI — the backend supports actually deleting a B2B member (DELETE /api/v1/admin/b2b/:id), but the B2B Team admin page only offers toggling a member active/inactive. Worth confirming whether soft-delete-only is the intended policy.
Full audit pass (2026-08-05). A systematic sweep checked every search/filter config, interactive element, and hardcoded value across the app for the same "looks wired up but isn't" pattern that produced several of the fixes above. Beyond what's listed as fixed in this document, a handful of harmless items were found and intentionally left alone (not asked for, not affecting any live feature): a leftover debug console.log on the homepage, a few unused Redux cart reducers superseded by the async thunks actually in use, two components with dead buttons that aren't rendered anywhere in the app, and some stale commented-out code in userRoutes.js/Footer.jsx. None of these are live bugs.
Backend error-handling & auth hardening (2026-08-06). A second pass, triggered by a raw MongoDB error message (E11000 duplicate key...) leaking straight to the admin UI on a duplicate B2B email. Root cause: the global error handler only produced friendly messages in production — in development it returned the raw driver error unmodified. Fixed app-wide, so every duplicate-key and validation error now returns a clear, human-readable message (e.g. "This email address is already in use") regardless of environment, not just for B2B. While auditing the rest of the error-handling and auth code, two more real issues turned up and were fixed: the Admin/B2B "reset password after OTP" endpoint accepted the request without re-checking the OTP (only the expiry window), and request logging (morgan) was silently disabled outside development, so a production-run server produced zero access logs.
Customer auth rework & branded email templates (2026-08-09). Customer login/signup moved from mobile-number OTP (which had never had a real SMS provider behind it — it only simulated delivery and accepted a universal 123456 bypass code) to real email OTP delivery via Resend, per a direct request to drop SMS OTP entirely. A new mandatory step now collects and validates an Indian mobile number right after email verification, before a full login session is granted — see Section 2. Separately, every transactional email the platform sends (not just the new customer flow) was rebuilt from plain unstyled text onto one shared branded HTML template — see Section 7.
